# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

KMS-PLC is a Windows/C++ toolset for building and converting PLC programs (TRiLOGI PC6) and HMI
projects (Weintek EasyBuilder Pro / "EBPro"). It reads plain-text "source" definitions of a PLC's
addresses, sequences, timers, and labels and generates/patches the corresponding files inside a
TRiLOGI `.PC6` project and an EBPro `.emtp` project (address lists, labels, .csv exports), keeping
the PLC program and the HMI project in sync. It also drives editing, importing, exporting, and
programming the physical PLC via the CLI tool `KMS-PLC.exe`.

## Prerequisites / one-time setup

This is a Visual Studio 2022 (17.2+) C++ solution. It depends on two sibling KMS products
(`KMS-Framework`, `KMS-Tools`) that are **not** committed to this repo — `Import/` and
`Installer/` are gitignored and populated by an external import tool (`KMS-Import.exe`, run from
the product folder). **The solution will not compile until `Import/Includes/KMS/...` and
`Import/Libraries/...` exist.** If `Import/` is missing, that's expected on a fresh clone; treat
build failures rooted in missing `KMS/*.h` headers as a missing-import problem, not a code bug.

Building also requires:
- Visual Studio 2022 Professional (MSBuild path referenced by `KMS-Build.cmd` assumes this edition)
- "Microsoft Visual Studio Installer Projects 2022" extension (for the installer project)
- Inno Setup 6 (`Compil32.exe`) to package the installer (`Product_x64.iss`)

## Build

Open `Solution.sln` in Visual Studio, or build from the command line. Configurations are
`Debug`, `Release`, `Release_Static` (platform `x64`; `Win32`/`x86` mappings exist in the .sln but
are not part of the standard build per `KMS-Build.cfg`).

```
MSBuild.exe Solution.sln /target:rebuild /Property:Configuration=Debug /property:Platform=x64
MSBuild.exe Solution.sln /target:rebuild /Property:Configuration=Release /property:Platform=x64
MSBuild.exe Solution.sln /target:rebuild /Property:Configuration=Release_Static /property:Platform=x64
```

`KMS-Build.cmd` runs the full release pipeline (build all 3 configs, verify expected outputs
exist, run the test binary, package with Inno Setup). It's generated by KMS-Framework's build
tool from `KMS-Build.cfg` — treat that config file, not the `.cmd`, as the source of truth for
what libraries/binaries/tests belong to the product.

## Tests

Tests use the KMS-Framework `Test::TestManager` harness (`KMS-PLC-A-Test`, entry point in
`KMS-PLC-A-Test/KMS-PLC-A-Test.cpp`). Run the built test executable directly, filtering to the
automated group:

```
x64\Debug\KMS-PLC-A-Test.exe Groups+=Auto
```

Test fixtures live under `Tests/` (e.g. `Tests/Test01/`), each a self-contained folder with a
`KMS-PLC.cfg`, a source `.PC6.txt`/label definitions, and (for EBPro-related tests) exported
`.csv`/`.mlb` artifacts under an `EBPro`/`HMI`/`PLC` subfolder. When adding test coverage for a
builder/converter, follow the existing `TestNN` folder convention rather than inventing a new
fixture layout. Files with a `// TEST COVERAGE  <date>  <author>` header comment indicate the file
has dedicated automated tests; `// NOT TESTED` markers on functions/branches call out known gaps.

## Architecture

The solution is organized as a small set of static libraries plus thin CLI-tool executables built
on top of them:

- **`Common/`** — shared headers only (no .cpp), defining the on-disk/text vocabulary shared
  across libraries: `Common/PLC/*` (element, function, sequence, timer, builder base class),
  `Common/EBPro/*` and `Common/TRiLOGI/*` (list types per project format), `Common/HMI/*`.
  `Common/Builder.h` defines the abstract `Builder` base (`AddSource(s)` + `Build()` +
  `ReadSource()`) that all format-specific builders derive from.
- **`PLC/`**, **`EBPro/`**, **`HMI/`** — small static libraries implementing the base/shared logic
  declared in `Common/` for each domain (generic PLC building blocks, EBPro config parsing, HMI
  label building).
- **`KMS-PLC-A/`** — the core static library with the real logic: TRiLOGI project model
  (`TRiLOGI_*.cpp` — Project, PC6 file, BitList/WordList/ConstantList/CounterList/TimerList,
  Function, Object), EBPro project model (`EBPro_*.cpp` — Project, Address(List), Function(List),
  Label(List), DataPtr, Software), plus `System.cpp` (the `System` class driving
  Clean/Edit/Export/Import/Program/Verify/Write), `Console.cpp` (colored CLI output helpers),
  `Convert.cpp`/`Parser.cpp` (string/text conversion utilities), and `Builder.cpp`/`Address*.cpp`.
  Nearly everything else in the tree consumes this library.
- **Standalone CLI executables**, each a thin `main()` wrapping one `Builder`/`System` from
  `KMS-PLC-A`:
  - `KMS-PLC` — the main CLI (`System::Main`), driven by `KMS-PLC.cfg` + command line
    (`Clean`, `Edit emtp|PC6`, `Export`, `Import`, `Program PLC`, `Verify`, `Write`).
  - `EBPro_Build_Address`, `EBPro_Build_Label` — generate EBPro address/label artifacts from
    source text files, via `Builder_Address`/`Builder_Label`.
  - `EBPro_Convert_Address`, `EBPro_Convert_Label` — convert/reformat EBPro exports.
  - `TriLogi_Build` (binary name `TRiLOGI_Build`) — builds/patches the TRiLOGI `.PC6` project via
    `TRiLOGI_Builder`.
  - `TriLogi_Convert` (binary name `TRiLOGI_Convert`) — converts TRiLOGI exports.
- **`KMS-PLC-A-Test/`** — the automated test suite (KMS `Test::TestManager`), exercising the
  `KMS-PLC-A` library against fixtures in `Tests/`.
- **`Scripts/`** and **`Templates/`** — `.cmd` scripts and config templates for driving EBPro/
  TRiLOGI conversion/build steps outside Visual Studio (e.g. `Scripts/EBPro_Convert.cmd`,
  `Templates/TRiLOGI_Build.cmd`), packaged with the installer (see `KMS-Build.cfg` `Folders +=`).

### Key concepts

- **TRiLOGI vs EBPro**: TRiLOGI is the PLC ladder-logic IDE/runtime (`.PC6` project file, Modbus
  1x/4x addressing); EBPro is Weintek's HMI designer (`.emtp` project). `System` (in
  `KMS-PLC-A/System.cpp`) owns one `mTRiLOGI` and one `mEBPro` instance and coordinates them —
  e.g. `Verify()` cross-checks that every Modbus address the HMI (`mEBPro.mAddresses`) references
  actually exists in the PLC (`mTRiLOGI.VerifyAddress_1X/4X`).
  - This same PLC/HMI address cross-check is what `Common/PLC/PLC.h`'s `PLC_Circuits.txt` /
    `PLC_Main.txt` source files ultimately feed into.
- **Builder pattern**: every code-generation tool (`Builder_Address`, `Builder_Label`,
  `TRiLOGI_Builder`) derives from `Builder` (`Common/Builder.h`): sources are added via
  `AddSource(s)`, parsed via the derived class's `ReadSource()`, then `Build()` emits/patches the
  target project file(s). When adding a new generator, follow this same shape rather than a
  bespoke entry point.
- **Precompiled-header-style `Component.h`**: each project has its own `Component.h` that pulls in
  `KMS/Base.h` plus that project's common local/import includes; project `.cpp` files start with
  `#include "Component.h"`, not the individual headers directly.
- **File header convention**: every source file starts with an author/copyright/license/product/
  file-path comment block. Match this exactly when adding new files (see any existing `.h`/`.cpp`
  for the template).
- **`KMS-PLC.cfg`**: the runtime config file for the `KMS-PLC` CLI (parsed via
  KMS-Framework's `CLI`/`Cfg` machinery), one per project/test folder — this is what
  distinguishes one PLC+HMI project pair from another.

## Dependency on KMS-Framework

This project is one of several "KMS" products built on a shared in-house framework
(`Import/Includes/KMS/...`: `CLI`, `DI`/`DI2`, `Cfg`, `Test`, `Console`, `File`, `Modbus`, etc.).
Idioms like `KMS_MAIN_BEGIN`/`KMS_MAIN_END`, `KMS_EXCEPTION*`, `KMS_BANNER`, and the
`DI::Object`/`Configurable` entry/module registration pattern seen in `System::System()` come from
that framework, not from this repo — don't try to redefine or "fix" them locally; consult the
framework headers under `Import/Includes/KMS/` (after import) to understand their contracts.
